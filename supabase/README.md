# Supabase setup: database, read endpoint, hourly ingest

```
pg_cron (hourly, 4 batches) --> Edge Function `ingest` --> NWS API
                                        |
                                        v
                                   Postgres tables  <--  REST API / rpc/observations_as_of  <--  GitHub Pages site
```

| File | What it is |
|---|---|
| `migrations/20261112000000_init.sql` | Tables (`stations`, `observations`, `polls`), row-level security, and the read function `observations_as_of` |
| `make_seed.py` -> `seed.sql` | Loads the 667 stations from `../observations.json` |
| `functions/ingest/` | The ingest Edge Function (`index.ts` = Supabase glue, `core.ts` = logic, `nws.ts` = NWS client) |
| `migrations/20261112010000_poll_frames.sql` | Read function `poll_frames`: one map snapshot per past ingest round, for the website's time slider |
| `migrations/20261112020000_schedule_ingest.sql` | Hourly schedule via pg_cron + pg_net (applied by `db push` like the rest) |
| `functions/ingest/core.test.ts` | Unit tests: `node --test supabase/functions/ingest/core.test.ts` |

## One-time setup

1. **Create a project** at supabase.com (free plan). Note the *project ref* (the `abcd...` in `abcd.supabase.co`),
   and from Project Settings -> API the public **anon/publishable key**.
2. **Link and create the tables** (from the Pipeline folder):
   ```bash
   supabase login
   supabase link --project-ref <PROJECT_REF>
   supabase db push
   ```
3. **Load the stations:** `.venv/bin/python supabase/make_seed.py`, then paste `supabase/seed.sql` into the
   dashboard's SQL editor and run it.
4. **Set the function secret and deploy:**
   ```bash
   supabase secrets set INGEST_SECRET=$(openssl rand -hex 32)   # then copy this value for step 6
   supabase functions deploy ingest --no-verify-jwt
   ```
   The function reads `SUPABASE_URL` and the service-role key from the environment that Supabase provides. If a run
   fails with a missing-key error, set it yourself: `supabase secrets set SERVICE_ROLE_KEY=<service role / secret key>`.
5. **Test it by hand** (should return JSON with `new_rows` > 0):
   ```bash
   curl -X POST "https://<PROJECT_REF>.supabase.co/functions/v1/ingest?batch=0&of=4" -H "x-ingest-secret: <INGEST_SECRET>"
   ```
   Run it for `batch=1,2,3` too, or just wait for cron.
6. **Schedule it:** make sure the Vault secret is named `INGEST_SECRET` (case-sensitive, same value as the function
   secret), then `supabase db push` applies the schedule migration. No SQL editor step. The project URL is written
   into the migration; it isn't a secret.

## Reading the data (from the website)

The anon key is meant to be public; row-level security makes the tables read-only for it.

```js
const SB = "https://<PROJECT_REF>.supabase.co/rest/v1";
const KEY = "<ANON_OR_PUBLISHABLE_KEY>";
const headers = { apikey: KEY, "Content-Type": "application/json" };

// Current map: latest reading per station, no older than 3 h
const now = await fetch(`${SB}/rpc/observations_as_of`, { method: "POST", headers, body: "{}" }).then(r => r.json());

// The map at a past time, accepting readings up to 6 h old
const past = await fetch(`${SB}/rpc/observations_as_of`, { method: "POST", headers,
  body: JSON.stringify({ as_of: "2026-11-12T18:00:00Z", max_age: "6 hours" }) }).then(r => r.json());

// One station's history
const hist = await fetch(`${SB}/observations?station_id=eq.KSLC&observed_at=gte.2026-11-11T00:00:00Z&order=observed_at.desc`, { headers }).then(r => r.json());

// Is the pipeline healthy?
const polls = await fetch(`${SB}/polls?order=started_at.desc&limit=8`, { headers }).then(r => r.json());
```
Each row from `observations_as_of` has `station_id, name, lat, lon, temp_f, observed_at, age_minutes`.

## The website (`../docs/`)

`docs/index.html` is a static page (no build step) that reads the database through the REST API and draws the map.
- **Most recent refresh** (top-left card): the newest successful ingest run, from the `polls` table.
- **Time slider:** one frame per ingest round (`poll_frames`), oldest to newest, with play/pause, prev/next, arrow keys
  and a "last 24 h / 2 days / 7 days" selector. The color scale is fixed across all frames so they're comparable.
- It re-reads the database every 10 minutes while open, and always on page load. All times are Mountain time.
- `docs/utah.json` (state outline + counties) is generated by `build_site_geo.py`; re-run only if you change the area.
- The key in `index.html` is Supabase's public *publishable* key. It's meant to be in browser code; row-level security
  keeps the tables read-only. Never put the service-role/secret key or `INGEST_SECRET` in `docs/`.
- To publish: push the repo to GitHub, then Settings -> Pages -> Deploy from a branch -> `main` / `/docs`.
- Local preview (the page must be served, not opened as a file): `cd docs && python3 -m http.server 8000`.

## Things to know

- **Storage:** about 120 bytes/row and ~50k new rows/day => the free 500 MB lasts roughly 2-3 months. See the
  optional retention job in the schedule migration.
- **Free plan pausing:** Supabase says free projects pause after a week of inactivity. Whether the hourly cron counts as
  activity is not something I verified; if the project pauses, resume it from the dashboard.
- **Edge Function limits:** 2 s CPU per call (150 s wall clock) on the free plan, which is why the stations are split
  into 4 batches. If a call ever hits the CPU limit (e.g. after a long outage, when the catch-up window is large),
  raise `of=4` to `of=8` in the schedule migration (and schedule 8 jobs).
- **Missed runs:** each batch asks NWS for everything since its last successful run (minus a 30 min overlap, max 24 h),
  and duplicates are ignored, so a late or skipped hour is filled in by the next run.
